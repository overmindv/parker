# Parker infrastructure boundaries

## Намерение

Оставить в бизнес-сервисах предметную логику, а повторяемую инфраструктуру
сосредоточить в Parker без появления общей сетевой точки отказа.

## Подходы

Рассмотрены центральный runtime-сервис, набор независимых подпакетов и встроенная
библиотека со стабильным корневым фасадом. Выбран третий вариант: он сохраняет
текущие импорты, не создаёт runtime bottleneck и позволяет постепенно раскладывать
реализацию по `internal/*`.

## Границы

Parker владеет lifecycle, config, logging, transport primitives, observability и
общими adapters. Бизнес-типы и специфичные гарантии остаются в сервисах. В этом
срезе меняются только Parker, users, tasks и recommendations; task-hunter и сервисы
Леонида исключены.

## Критерии

Публичный API совместим, реализация env/health/logging находится в логических
пакетах, тесты/сборки зелёные. Production-сервис без Kafka не требует Kafka TLS,
но создание Kafka client без TLS по-прежнему отклоняется. Tasks обновляется только
вместе с owner migrations для lease/retry outbox и TLS consumer config. Релиз новой
структуры и обновление сервисов выполняются отдельно после проверки совместимости.
