# 08 — Ключевой результат: workflow создания нового сервиса (Части 1–5)

Это целевой сценарий **конечного пользователя parker** — разворачивание нового сервиса.
После реализации паркера (Фазы 0–7) создание сервиса сводится к шагам ниже. План писан под
**реальную локалку проекта** (docker-compose + GitHub Actions); под каждым шагом в скобках
указан «платформенный аналог» (Vault / `.o3/k8s` / Grafana / GitLab) — если платформа появится,
шаг маппится один-в-один, сейчас он выполняется локальными средствами.

> Для агента: это **спецификация результата**, а не фаза разработки самого parker.
> Реализация самого parker — Фазы 0–7 (файлы 01–07, 09). Этот файл задаёт «definition of success».

---

## Часть 1 — Подготовка (руками, один раз на сервис)

1. **Создать репозиторий `overmindv/<service-name>`** — новый git-репозиторий в группе `overmindv`,
   соседний с `tasks`, `users`, `media` и т.д.
   - Название: lowercase, kebab-case, ≤40 символов (как валидирует `parker init`).
2. **Kafka-топики (если нужны)** — сейчас топики заводит `kafka-topics` сервис в `infra/docker-compose.yml`.
   - Добавить запись в конфигурацию `kafka-topics` (topic name, partitions, retention),
     повторить `make up`.
   - *(Платформенный аналог: тикет на создание топика в продакшен-kafka.)*
3. **Секреты и Vault-роль (если нужны)** — сейчас секреты живут в `infra/.env`
   (`scripts/prepare-env.sh` генерирует значения по `__GENERATE__`-маркерам).
   - Добавить `SVC_*_TOKEN=__GENERATE__` (или явное значение) в `infra/.env.example` → `make up` сгенерирует.
   - *(Платформенный аналог: завести Vault-роль и выдать секреты сервису.)*

---

## Часть 2 — Инициализация и инфраструктура сервиса

1. **Клонировать репозиторий**: `git clone .../overmindv/<service-name>` (пустой).
2. **`parker init <service-name>`** (из `overmindv/parker`):
   ```
   ../parker/bin/parker init <service-name> --pg [--kafka]
   ```
   → генерирует go.mod (с `replace => ../parker`), `cmd/<svc>/main.go`, `internal/`, `Makefile`,
   `Dockerfile`, `migrations/`, `.github/workflows/ci.yml`, `.env.example`, README; печатает compose-блок.
3. **Настроить конфиг и развёртывание** *(аналог `.o3/k8s/values*.yaml`)*:
   - В `infra/docker-compose.yml` вставить напечатанный блок сервиса (`<svc>-postgres`,
     `<svc>-migrate`, `<svc>`).
   - В `infra/.env.example` добавить `SVC_*`-переменные; топики — в `kafka-topics` (если `--kafka`).
4. **Добавить `migrations/`, `datafixes/`, `CODEOWNERS` (если надо)**:
   - `migrations/` — уже есть (пустой `0001_init.sql`); дописать схемы сервиса.
   - `datafixes/` — каталог для datafix-SQL (по конвенции Overmindv) — создать при необходимости.
   - `CODEOWNERS` — владельцы репозитория.
5. **Настроить CI**: `.github/workflows/ci.yml` сгенерирован (lint/test/build/component + e2e).
   Проверить переменные окружения для component-джоба (`COMPONENT_TEST_DSN`), при необходимости
   адаптировать e2e-делегирование `overmindv/tests`.
6. **Запушить, проверить пайплайны** — открыть MR/PR, дождаться первых запусков.

---

## Часть 3 — Пайплайны зелёные

Готово, когда в GitHub Actions (или на платформе CI) зелёные джобы:
- `lint` (golangci-lint), `test` (`make test`, без Docker), `build` (`make build`),
- `component` (поднятый postgres:17, `parker migrate up` + component-тест),
- `e2e` (делегируется `overmindv/tests`, по желанию).

⚠️ Если пайплайн красный на этом этапе — это дефект генератора/паркера, а не сервиса:
чинить в `overmindv/parker`, а сервис перегенерировать.

---

## Часть 4 — Наблюдаемость

1. **Grafana dashboard** — сейчас Grafana как сервиса нет:
   - Проверить, что `GET /metrics` отдаёт `parker_*` метрики.
   - Импортировать `docs/dashboard.json` (из parker) при появлении Grafana; сейчас файл — готовый ассет.
   - *(Платформенный аналог: зайти в Grafana, импортировать dashboard по метрикам parker.)*
2. **Алерты** — воспроизводимый алертинг пока отсутствует:
   - Убедиться, что `/ready`, `/health` ведут себя корректно (503 при падении зависимостей).
   - Заготовка `docs/alerts.example.yml` (Prometheus-правила) — приложить к сервису на будущее.
   - *(Платформенный аналог: завести алерты в системе алертинга по правилам выше.)*
3. **Логи и трейсинг**:
   - Проверить JSON-логи в `make logs <svc>`: есть `request_id`, `trace_id` (если `traceparent` во входе).
   - Прогнать пару запросов, посмотреть access-лог и `/metrics` (RPS, p99, error rate).

## Часть 5 — Реализация бизнес-логики

В сгенерированном каркасе разработчик заполняет **только бизнес-логику**:
```
internal/pkg/
  domain/       — бизнес-типы и инварианты
  usecase/      — сценарии, транзакции (boundary транзакций — здесь)
  store/        — persistence-интерфейс
  adapter/      — реализация на pgx (хранится в сервисе)
app/            — HTTP-обработчики, регистрируются на app.HTTP()
migrations/     — SQL-миграции сервиса (append-only)
cmd/<svc>/main.go — уже написан: parker.Main(run, ...); внутри — регистрация роутов/чекков/воркеров
```

**Инвариант**: в прикладном сервисе НЕ появляется инфраструктурного кода —
config-подсистемы, HTTP-сервера, lifecycle, миграционного тулинга. Всё это в parker.
Любое появление такого кода в сервисе — сигнал вынести в parker.
