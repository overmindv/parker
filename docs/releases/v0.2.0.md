# Parker v0.2.0 — надёжная доставка событий

## Изменения

- Kafka consumer не подтверждает offset через неуспешную запись: три обработки,
  bounded backoff, защита rebalance и остановка Runnable при commit failure (OVM-181).
- PgOutbox: durable lease 30 секунд, claim token и CAS ack; crash допускает безопасный
  дубль, stale worker не подтверждает новый claim (OVM-182).
- Persistent retry с jitter, восемь ошибок до exhausted, generation-CAS replay с
  audit, queue-age metric и ограниченная retention sent (OVM-183).
- Общие TLS/SASL настройки producer/subscriber; TLS обязателен в production,
  PLAIN/SCRAM только поверх TLS, CA/hostname verification не отключается (OVM-184).
- Standalone init без обязательного replace, timestamp migrations, no-PG вариант,
  исправленный healthcheck и тест сгенерированного handler (OVM-186).

## Совместимость

Go 1.26 и module path `github.com/overmindv/parker` сохранены; зависимости go.mod
не изменились относительно v0.1.0. Main/App/Option/Runnable/HealthCheck и минимальный
Outbox interface сохранены. Новые поля Options/OutboxRecord требуют keyed literals
у внешних пользователей. Variadic Kafka constructors и NewOutboxDispatcher совместимы
с обычными вызовами, но function-value adapters прежней сигнатуры требуют wrapper.

Поведение изменено намеренно: production plaintext Kafka отвергается, PgOutbox
требует owner migrations, MarkSent для leased IDs заменяется на MarkClaimSent.
Custom Outbox adapters совместимы по коду, но не получают leases/retries автоматически.
Это pre-1.0 minor release; не выполнять слепой rolling update старых/new workers.

## Подключение

```bash
go get github.com/overmindv/parker@v0.2.0
go mod tidy
go test -race ./...
go build ./...
```

Коммитить go.mod/go.sum без replace. Init использует опубликованный bootstrap v0.1.0;
после init выполните go get выше. `make release-check RELEASE_VERSION=v0.2.0` создаёт
сервис в temp directory, подключает именно опубликованный тег, проверяет отсутствие
replace, сборку/тесты и runtime version. Template pin отделён от candidate version,
чтобы CI до публикации не зависел от ещё не существующего тега.

## Миграция стандартного outbox

1. Инвентаризировать владельцев таблицы: Tasks activity outbox и Content используют
   PgOutbox. Execution outbox Tasks и собственный CatalogOutbox Entities не мигрируются
   этими SQL. Проверить snapshot/резервную копию владельца перед rollout.
2. Добавить **новые** goose migrations владельца из
   `docs/migrations/202611160001_outbox_leases.sql` и
   `docs/migrations/202611160002_outbox_retries.sql`. При необходимости выбрать свободные
   YYYYMMDDNNNN номера. Не редактировать уже применённые файлы.
3. Применить schema expansion до новой версии приложения. Столбцы nullable/default,
   существующий payload не переписывается. Проверить индексы retention/queue age.
4. Остановить старые outbox workers и дождаться завершения publish. Не смешивать старый
   без-token алгоритм с новой версией. Настроить TLS/SASL и topic/group ACL для production.
5. Обновить require по тегу, запустить новые workers. Для метрики передать App.Metrics()
   в необязательный аргумент NewOutboxDispatcher. Проверить очередь/lease/exhausted.
6. Replay делать только после авторизации operator, с expected generation и actor UUID.
   Payload и broker credentials не помещать в audit/logs.

## Rollback

Остановить все новые workers и дождаться окончания публикаций. В транзакции владельца:

```sql
UPDATE outbox
SET status='pending', claim_token=NULL, lease_until=NULL
WHERE status='publishing';
```

Затем запускать старую версию. Столбцы и audit сохранить; migrations Down намеренно
не удаляют данные. `exhausted` не переводить в pending автоматически: требуется
решение оператора. At-least-once допускает дубликаты после ack/crash, consumers должны
быть идемпотентны. Retention удаляет sent старше семи дней; вернуть уже удалённые
sent при rollback нельзя, поэтому историю при необходимости экспортируют заранее.

## Выпуск

После зелёного main CI создать annotated tag v0.2.0 на проверенном commit и отправить
его в origin. Release workflow проверяет version/tag, build/test/lint, PostgreSQL и
Kafka, а также generated consumer по опубликованному тегу, затем создаёт GitHub Release.
Тег не перемещается: исправления после публикации выпускаются новой версией.
